## 실제 적용 결과

두 에이전트는 서로 다른 프로젝트를 맡았고, 각각 초기 작성과 후속 요청을 같은 문맥에서 수행했다. 따라서 독립된 표본 4개나 무작위 A/B가 아니라, 두 프로젝트에서 이어진 네 단계의 관측이다. 모델·추론 설정의 별도 override는 하지 않았다.

| 사례 | 이번 단계에서 새로 읽은 스킬: 에이전트 보고 | 문서에서 직접 확인한 결과 | 사전 기준과의 관계 |
| --- | --- | --- | --- |
| S1 | 없음 | 명백한 입력 오류는 두 문장으로 정의. 저장·인증·네트워크 구조 없음. 정밀도·큰 수 범위는 미정 | 일치 |
| S2 | 없음 | 결과 라벨을 ‘합계’로 한다는 한 줄만 추가. 기획 파일 해시와 나머지 명세 유지 | 일치 |
| R1 | `specify-failure-recovery` | 결과 불확정·최신 입력 보존·계정 경계·늦은 응답·해제 갱신 사건 포함. 재시도·종료 후 보존·만료 후 편집·담당은 미정 유지 | 일치 |
| R2 | `review-release-evidence` | V1 근거를 V2 PASS로 전용하지 않음. V2 제한 운영 인계 완료와 실제 복구 미검증·C2 공백을 분리. 재개 사건과 제안 상한 명시 | 일치 |

R2에서는 이전에 읽은 복구 지침과 기존 계약을 문맥에서 재참조했다고 보고했으며 다시 읽지 않았다. 이를 새 파일 로딩이나 계약 전체 재검토로 세지 않는다. 부모 검토자는 R2 전후 기획·명세의 해시 일치, 두 시험 폴더의 `AGENTS.md`가 기준본과 같은지 확인했다. 문서 외의 산출물은 없었다.

에이전트가 보고한 선택 이유는 S1의 “발생·해제가 명백한 입력 형식 오류”, S2의 “단순 라벨 수정”, R1의 “저장 실패·응답 유실·인증 만료의 보존→복구→해제 계약”, R2의 “후보별 시험 근거와 위험 수용을 구분”이었다. 실제 작성 문서와 이 이유가 일치하는지 검토했다. 전체 도구 호출 trace를 독립적으로 계측한 결과라고 주장하지 않는다.

## 후속 입력

S2 요청은 “기존 동작은 그대로 두고 결과 영역의 표시 라벨을 ‘합계’로 한다는 요구 한 문장만 추가하고, 수정이 완료되면 바뀐 내용과 확인 결과를 짧게 보고”였다. 일상적인 문서 작업 완료가 릴리즈 판단으로 확대되는지 확인했다.

R2에는 다음 가상 사실만 추가했다. V1/H1은 실제 브라우저 정상 저장 통과, V2/H2는 정적 검사·저장소 모의 시험만 통과했고 응답 유실·만료 후 실제 복구는 미실행이다. V2 UI 번들에는 C2가 표기됐으나 공개 refs와 정확 SHA 조회로 확보하지 못했다. 운영 담당은 이 두 공백을 수용해 소수 사용자 시범 운영을 승인했고 수동 동일 계정 재로그인은 허용했으며 자동 복구 보장은 승인하지 않았다. 기존 기획·명세 변경 없이 인계 범위와 재개 조건을 문서로 판단하도록 요청했다.

## 보완 판정과 한계

관측한 네 단계에서는 사전 기준을 벗어난 스킬 선택이나 핵심 복구 계약의 누락을 확인하지 못했다. 이 결과만으로 새 금지 규칙이나 필수 검토 단계를 추가할 근거는 없다. 두 스킬 본문과 세 프로젝트 템플릿은 그대로 유지하고, 적용 예시와 이 검증 기록을 안내서에 연결했다.

이 시험은 앱 설치·제품/시험 코드 개발·실제 서버/브라우저 실행·배포를 포함하지 않는다. 다른 프로젝트에서의 모든 정책 누락, 긴 문맥 이후의 선택, 스킬 미설치·상충 지침 상황은 시험하지 않았다. 이 표본을 보편적인 무누락·무과잉 보증이나 성능 개선율로 해석하지 않는다. 다음 실제 요청에서 새로운 오선택이나 계약 누락이 관측될 때 그 조건만 좁게 보완한다.
