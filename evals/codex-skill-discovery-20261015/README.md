# 실제 Codex 동명 스킬 검색·선택 시험

기준일: 2026-10-15. 게시 기준 커밋: `fa2949cb434e6f962dfaf183171dbed5647e133f`.

설치된 **Codex CLI `0.162.0-alpha.17.2`, Windows**에서 실제 검색과 모델의 파일 읽기를 관측했다. 이전 [문서 호환성 시험](../skill-compatibility-20261015/README.md)에서 미검증으로 남긴 범위 중 일부의 후속 확인이다. 새 앱·CLI·패키지는 설치하지 않았다. 기존 개인 스킬과 설정을 이동·수정·삭제하지 않았으며 제품 개발·실기 조작도 하지 않았다.

## 결론 먼저

- 다섯 이름 모두 개인본·프로젝트 루트본·하위본이 **함께 검색됐다**. 동명본이 자동 병합되거나 가까운 본만 남는다고 가정할 수 없다.
- 하위 폴더에서 이름만 지정한 이번 명시 호출은 다섯 이름 모두 하위본을 읽었다. 그러나 검색 목록에서는 루트본이 하위본보다 먼저였다. **목록 순서와 실제 읽은 경로는 다르다.**
- 같은 충돌 상태에서 개인본의 정확한 파일 경로를 지정한 대조는 그 개인본만 읽었다.
- 이것은 제한된 CLI 관측이다. **“항상 하위 > 루트 > 개인”이라는 엔진의 보장된 우선순위를 입증한 것은 아니다.** Desktop 선택기 클릭, 암묵적 설명 매칭, 다른 버전·OS는 미검증이다.

## 환경·시험 자료

실제 개인 설치본은 `USER_SKILLS`, 스킬 없는 임시 Git 프로젝트는 `BASELINE_CWD`, 동명 파일을 둔 임시 Git 루트는 `ROOT_CWD`, 그 안의 하위 작업 폴더는 `NESTED_CWD`로 익명화했다. 이 PC에서 `USER_SKILLS`는 기존 `.codex/skills` 위치이며 별도 개인 설치 위치를 새로 만들지 않았다.

프로젝트 루트와 하위 폴더의 `.agents/skills/`에는 다음 다섯 **동일 name**을 갖는 합성 탐침을 각각 만들었다.

`specify-failure-recovery`, `review-release-evidence`, `coordinate-device-validation`, `verify-powershell-handoff`, `diagnose-computer-use-recovery`.

이 탐침은 배포 스킬의 복제·업데이트본이 아니다. description은 읽기 전용 검색 시험으로 같게 제한하고, 본문에는 `ROOT_<name>` 또는 `NESTED_<name>` 표식만 달았다. 개인본은 원래 내용 그대로다. 따라서 결과는 이름 충돌과 경로 선택에 관한 것이며 실제 전문 업무의 품질 비교가 아니다. 정확한 구성과 요청은 [시험 자료](fixture-spec.md)에 있다.

## 실제 검색 결과

설치된 바이너리의 별도 `app-server --stdio` 프로세스에 공식 JSON-RPC 초기화를 하고 `skills/list`를 `forceReload: true`로 요청했다. 앱을 재시작하거나 전역 검색·활성화 설정을 바꾸지 않았다.

| 조회 CWD | 전체 반환 수 | 각 대상 이름에 함께 반환된 경로 | 대상 오류 |
| --- | ---: | --- | --- |
| BASELINE_CWD | 26 | USER_SKILLS 1개 | 없음 |
| ROOT_CWD | 31 | 루트 1개 + USER_SKILLS 1개 | 없음 |
| NESTED_CWD | 36 | 루트 1개 + 하위 1개 + USER_SKILLS 1개 | 없음 |

다섯 이름 모두 같은 패턴이었다. 루트 조회에는 하위 전용본이 나오지 않았고 하위 조회에는 상위와 하위본 모두 나왔다. NESTED_CWD 응답의 대상 항목은 이름별 루트→하위, 그 뒤 개인 범위 순이었다. 이는 **이번 API 반환 순서**이며 선택기 UI 정렬이나 실행 우선순위 규약으로 바꾸지 않는다. 전체 수에는 대상 외 설치 스킬도 포함되며 Desktop의 전체 카탈로그 수와 동일하다는 주장은 하지 않는다.

[catalog.json](catalog.json)은 실제 응답에서 다섯 이름을 필터링하고 개인 경로만 별칭으로 바꾼 기록이다. 원래 응답의 `catalogIndex`, scope, enabled와 오류 목록을 유지했다. [catalog-probe.mjs](catalog-probe.mjs)는 사용한 읽기 전용 조회 클라이언트다. 기존 서버의 설정 변경 API는 호출하지 않으며 자신이 시작한 자식 stdio 프로세스만 종료한다.

## 실제 명시 선택과 읽기

CLI의 비영속 `exec --ephemeral --json --sandbox read-only`, 승인 요청 `never`, `--no-daemon`, CWD=NESTED_CWD로 총 세 번 실행했다. 모델·추론 설정은 별도로 지정하지 않고 기존 CLI 기본값을 사용했다. 실제 해결된 모델 ID를 이 이벤트에서 별도로 확인하지 않아 모델별 우선순위 비교로 해석하지 않는다. 프롬프트에는 설치·쓰기·설정 변경·helper 실행·외부 도구 사용·제품 작업을 금지했다. Codex의 모델 요청과 GitHub 게시 자체에는 정상적인 서비스 통신이 필요하며 오프라인 시험이라는 뜻은 아니다.

| 실행 | 지정 방식 | 실제 완료된 파일 읽기와 결과 |
| --- | --- | --- |
| S1 | `$review-release-evidence` 이름만 지정 | 하위 파일 `Get-Content` 성공, `NESTED_review-release-evidence` 보고 |
| S2 | 나머지 네 이름을 한 요청에 명시 | 네 하위 파일 각각 `Get-Content` 성공, 각각의 `NESTED_<name>` 보고 |
| S3 | 개인 `review-release-evidence/SKILL.md`의 정확한 경로를 일반 텍스트로 지정. `$name` 없음 | 해당 개인 파일만 읽음. 제목 `릴리즈 근거와 종료 판정`, 탐침 표식 없음 |

자기 보고만으로 채점하지 않았다. `--json`의 `command_execution` 시작·완료 이벤트에서 실제 경로·본문·종료코드 0을 확인하고 최종 표식과 대조했다. 세 turn 모두 완료됐으며, 보이는 모델 도구 실행은 위 여섯 파일 읽기뿐이었다. S2는 하나의 요청이므로 네 독립 세션 성공으로 세지 않는다. S1의 단일 이름과 S2의 묶음 요청도 동등한 반복 표본이 아니다.

[selection-observations.json](selection-observations.json)은 검토자가 확인한 이벤트의 구조화 요약이다. 원시 trace 전체가 아니며 개인 경로·세션 식별자·기존 스킬 본문 전체는 게시하지 않았다. 숨겨진 초기 프롬프트의 주입 내역이나 내부 resolver 분기는 관측하지 못했다. 따라서 **관측한 파일 선택**과 엔진의 결정적 이름 해석 규칙을 구분한다. S3도 일반 경로 지정 시험이며 API의 구조화된 `type: skill` 입력을 시험한 것은 아니다.

## 연결 한계와 보존 확인

기존 Desktop 공유 서버에 붙는 `app-server proxy`는 기본 샌드박스와 정상 권한 확인 모두 로컬 소켓 `os error 10050`으로 실패했다. ACL·소켓·환경을 고치거나 앱을 재시작하지 않고, 설치된 동일 CLI 바이너리의 독립 stdio 프로세스로 검색을 확인했다. 이는 **공유 Desktop 연결 복구가 아니며 현재 Desktop UI의 선택 동작을 직접 관측한 것도 아니다.** 보조 Node REPL도 초기화 실패해 사용하지 않았고 기존 Node로 작은 조회 클라이언트를 실행했다.

기존 다섯 스킬 패키지의 9개 파일과 사용자 `config.toml`·비어 있던 사용자 `AGENTS.md`, 총 11개 파일의 전후 SHA-256이 같았다. [보존 기록](preservation.json)에 익명 경로와 해시를 남겼다. 기존 제품 프로젝트에 쓰지 않았으며 임시 프로젝트에는 지침·합성 탐침만 만들었다.

`--ephemeral`은 세션 파일을 영속 저장하지 않는 실행 옵션이다. 정상적인 로그·캐시·임시 경로 처리까지 PC 전체가 무변경이었다고 주장하지 않는다. CLI의 기존 icon 경고와 PowerShell snapshot 미지원 경고는 turn 성공과 구분했으며 원인 분석·환경 수정으로 확대하지 않았다.

## 다른 프로젝트에 적용할 규칙

1. 이름만 같다는 이유로 한 본이 자동으로 덮어쓰거나 병합된다고 가정하지 않는다. 위치·내용·필요한 참조까지 비교한다.
2. 검색 목록의 첫 항목이나 현재 작업 폴더의 가까운 경로를 **보장된 선택 규칙**으로 사용하지 않는다. 재현성이 중요하면 쓸 파일 경로와 원본 커밋을 지정하고 실제 읽은 경로를 확인한다.
3. CLI·IDE·Desktop을 구현상 같다고 단정하지 않는다. 검증한 버전·CWD·입력 방식·전송 경로를 함께 기록한다.
4. 중복을 없애려고 기존 개인본을 자동 삭제하거나 전역 설정을 바꾸지 않는다. 승인된 설치/정리 작업에서만 결정한다.

이 범위의 실제 검색·선택 확인으로 종료한다. 자동 매칭률, 반복 안정성, UI 선택기, 캐시 무효화·재시작 효과, 플러그인/관리자/시스템 스코프와의 충돌, 대소문자·심볼릭 링크·동일 내용 복제본의 모든 조합은 시험하지 않았다. 필요한 특정 프로젝트에서 다른 결과가 관측될 때 그 조건만 후속 확인한다.
