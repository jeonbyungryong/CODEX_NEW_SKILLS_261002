# 프로젝트 작업 지침

현재 사용자 요청과 프로젝트의 승인 범위를 기준으로 작업한다. 단계 이름만으로 스킬·리뷰·시험을 자동 추가하지 않는다.

## 필요한 자료만 읽기

- 목적·운영 제약·제외 범위가 필요하면 [초기 기획](docs/project-brief.md)의 해당 절을 읽는다.
- 기능 동작·오류·인수 기준이 필요하면 [명세](docs/requirements.md)의 해당 요구를 읽는다.
- 문서가 없거나 미정이면 현재 요청에 필요한 부분만 작성한다. 작은 수정 때문에 전체 템플릿을 채우지 않는다.
- 개발 명령은 실제 프로젝트의 README·설정·기존 시험을 확인해 사용한다. 템플릿에 없는 도구나 명령을 추정하지 않는다.

## 두 스킬의 적용 조건

사용자가 이름으로 지정한 스킬은 요청 범위에 맞게 사용한다. 그 외에는 아래 조건을 충족할 때만 해당 스킬을 읽고 적용한다.

| 스킬 | 적용하는 조건 | 생략하는 경우 |
| --- | --- | --- |
| `specify-failure-recovery` | 이번 요청에서 오류·재시도·시간 만료·보존·초기화·비동기 완료·복구·해제 계약을 새로 정의하거나 변경·검토한다. 또는 해당 계약의 구체적 누락이 발견됐다. | 해당 동작에 영향 없는 오탈자·스타일·이름 수정, 단순 조회·설명, 이미 확인한 계약의 반복 보고. 보존·권한·비동기·재시도에 영향 없고 발생·해제가 명백한 입력 형식 오류도 직접 작성 |
| `review-release-evidence` | 이번 요청에서 소스·산출물·시험·승인이 같은 후보를 가리키는지와 완료·릴리즈·인계 범위를 판단한다. 또는 후보/시험 근거 충돌, 원본 재현 공백, 위험 수용, 새 관측 없는 프로젝트 검토 반복 때문에 다음 우선순위·종료 판단이 필요하다. | 일반 기능 구현·단위시험·초기 아이디어 정리·작업 완료 요약. 단일 시험의 시간 예산, 한 PowerShell 스크립트의 호환성, 개별 도구 오류 분류처럼 해당 전문 스킬만으로 답할 수 있는 검토 |

명시적 지정이 없으면 두 조건이 모두 성립할 때만 둘 다 사용한다. 기획 단계라는 이유로 첫 스킬을, 테스트나 커밋이 있다는 이유로 둘째 스킬을 일괄 호출하지 않는다. 위의 명백한 입력 형식 오류는 스킬을 생략하고 발생·해제를 두 문장으로 적는다. 스킬이 없으면 관련 계약을 직접 검토하고 설치 미확인을 짧게 알린다. 작업을 멈추거나 스킬을 자동 설치하지 않는다.

## 구현과 검토

- 요구 부재, 모호한 계약, 구현·통합·시험 누락, 승인된 추가 범위를 구분한다. 구현 방법이 명세에 없다는 이유로 사용자 요구 누락으로 판단하지 않는다.
- 미정 값에는 결정 담당·결정 시점·그 전 진행 범위를 적는다. 재시도 수치·권한·삭제 정책은 임의로 확정하지 않는다.
- 오류 계약을 다룰 때는 발생→보존→복구→해제와 상태/UI 갱신 사건을 연결한다. 재시작이 승인된 복구라면 재시작 후 사용 가능 상태를 확인한다.
- 변경한 동작에 필요한 기존 검사와 회귀 확인을 수행한다. 새 변경·실패·미해결 의문이 없으면 전체 시험이나 독립 리뷰를 반복하지 않는다.
- 추가 조사에는 바꿀 결정과 새 관측을 정한다. 전체 조사 상한은 도구·가설·리뷰 방법을 바꿔도 유지한다. 발견 수정분 확인 후 종료한다.
- 소스 확인·모의 시험·실제 환경 검증·사용자 위험 수용을 구분한다. 제공 불가능한 환경은 증명 범위를 한정하고, 현재 작업의 목적에 필요할 때만 대체 시험을 제안한다.
- 검토·문서화 요청으로 제품 수정·앱 설치·운영 데이터 변경·배포까지 확대하지 않는다. 기존 승인과 보호 대상은 유지한다.

## 결과 전달

변경 내용과 이유, 실제 수행한 확인, 남은 미정·미검증을 필요한 만큼만 전달한다. 승인된 범위의 완료와 향후 개선 제안을 구분하며, 스킬을 쓰지 않은 사소한 작업에 별도 체크리스트를 만들지 않는다.
