# 초기 기획부터 개발 검토까지 두 스킬 사용하기

`specify-failure-recovery`는 오류가 언제 발생하고 무엇을 보존하며 어떤 행동으로 해제되는지 명세하는 데 쓴다. `review-release-evidence`는 현재 후보의 근거, 남은 위험, 개발·검토 우선순위와 종료 여부를 판단하는 데 쓴다. 두 스킬 모두 지침 파일이며 별도 서버·에뮬레이터·실물 기기를 설치할 필요가 없다.

아래 요청의 `[내용]`을 프로젝트 정보로 바꾸고 필요한 단계만 사용한다. 작은 입력 검증에는 발생·해제 두 문장만으로 충분하다. 모든 기능에 전체 절차를 반복하지 않는다.

## 단계별 선택

| 단계 | 사용할 스킬 | 제공할 자료 | 기대 산출물 |
| --- | --- | --- | --- |
| 초기 기획 | `specify-failure-recovery` | 사용자·업무·환경·허용 중단·잃으면 안 되는 자료 | 운영 계약과 미정 결정 |
| 상세 명세 | `specify-failure-recovery` | 사용자 동작·정상 흐름·기존 오류 정책 | 발생→보존→복구→해제 계약 |
| 개발 순서 결정 | 두 스킬 | 명세·의존성·일정·검증 가능 환경 | 가장 위험한 사용자 경로와 먼저 확인할 가정 |
| 개발 중 검토 | `specify-failure-recovery` | 변경 파일·관련 명세·기존 시험 | 요구/구현/시험 누락 구분과 최소 보완 |
| 완료·인계 검토 | `review-release-evidence` | 같은 후보의 소스·산출물·시험·승인 근거 | 완료 범위·미검증·다음 우선순위 |
| 회고·반복 중단 | 두 스킬 | 수정 이력·판정 변화·추가 검토 제안 | 재사용 규칙과 이번 조사 종료 판단 |

## 1 초기 기획 요청

```text
$specify-failure-recovery를 사용해 [프로젝트 개요]의 초기 기획을 검토해줘.
사용자와 환경: [내용]
핵심 사용자 동작: [내용]
잃으면 안 되는 자료와 허용 중단: [내용 또는 미정]
정상 동작, 실패 시 사용자 영향, 허용 복구 행동, 다시 사용 가능한 조건을
한 페이지 운영 계약으로 정리해줘. 아직 결정하지 않은 정책은 임의로 채우지 말고
결정 담당 역할·결정 시점·그 전 진행 가능한 범위를 적어줘. 지금은 기획만 작성해줘.
```

사용자는 목적과 허용 가능한 손실을 정하고, 개발자는 이를 상태·관측·시험으로 구체화한다. 구현 방식이 없다는 이유로 사용자 기획 누락으로 돌리지 않는다.

## 2 상세 명세 요청

```text
$specify-failure-recovery로 [명세 파일 또는 첨부 내용]을 보완해줘.
범위: [저장/전송/로그인 등 이번 사용자 동작]
각 오류를 발생 전 상태·발생 사건·감지·보존 대상·자동/수동 복구·해제 조건·
UI 갱신 사건·재시도 중단·검증 방법으로 연결해줘.
요청 접수, 실제 처리, 영구 저장, 응답 도달이 다른 단계인지 확인하고
응답 유실·최초 정상본 부재·늦은 응답 중 해당 기능에 필요한 사례만 포함해줘.
숫자와 권한 정책은 확정/제안/미정으로 표시해줘. 제품 코드는 바꾸지 마.
```

예를 들어 잠금 시간이 지나도 비활성 버튼을 눌러야만 상태가 갱신된다면 해제가 완성되지 않았다. 반면 승인된 복구가 재시작이면 재시작 후 조작 가능 상태를 기준으로 삼는다.

## 3 개발 우선순위 요청

```text
$specify-failure-recovery와 $review-release-evidence로 아래 개발 순서를 검토해줘.
목표·완료 기준: [내용]
명세·현재 구현·의존성·일정: [파일 또는 내용]
사용 가능한 검증 환경과 제공 불가능한 자원: [내용]
사용자 영향과 데이터 보존 위험을 기준으로 먼저 확인할 경로를 골라줘.
정상 입력→실제 결과→저장→응답→핵심 실패의 복구를 연결하는 최소 작업부터 제안하고,
각 작업에 이유·선행 결정·완료 관측·미조치 영향을 적어줘.
현재 목표의 결정을 바꾸지 않는 새 도구·전체 재설계·추가 리뷰는 작업에 넣지 마.
```

상세 저장 기반이나 UI 기능 전체를 먼저 만들기보다 가장 위험한 연결을 먼저 확인한다. 보유하지 않은 장비에서만 증명할 수 있는 주장은 미검증으로 남기고, 현재 PC의 모의 시험이 증명하는 범위를 따로 적는다.

## 4 개발 중 변경 검토 요청

```text
$specify-failure-recovery로 [변경 파일/차이]와 [관련 명세/시험]을 검토해줘.
이번 변경의 목적과 범위: [내용]
오류 유발→자료 보존→복구→해제가 실제 호출자와 화면까지 이어지는지 확인해줘.
요구 부재, 모호한 계약, 구현·통합 누락, 시험 누락, 승인된 범위 변경을 구분해줘.
각 발견에는 파일·행 또는 원근거, 반례, 사용자 영향, 최소 보완과 필요한 검증을 적어줘.
현재 요청은 검토야. 발견한 모든 문제를 자동 수정하거나 전체 검증을 다시 실행하지 마.
```

수정까지 원하면 다음 요청에서 특정 발견과 파일 범위를 지정한다. 스킬을 호출했다는 사실 자체가 설치·운영 데이터 변경·배포를 승인하지는 않는다.

## 5 완료와 인계 요청

```text
$review-release-evidence로 [후보 버전/커밋]의 완료·인계 상태를 검토해줘.
소스·별도 구성요소·산출물·시험·최신 승인 자료: [파일/링크]
이번 완료 범위와 수용된 제한: [내용]
현재 결함·과거 해소·수용된 제한·미검증·개선 제안을 구분하고
각 완료 주장에 같은 후보의 근거가 연결되는지 확인해줘.
추가 조사가 실제로 바꿀 결정이 있을 때만 최소 다음 행동과 조사 상한을 적어줘.
제한 운영 승인과 시험 PASS를 구분하고, 현재 자료로 가능한 완료 판정을 내려줘.
```

문서나 단순 스크립트에는 APK·인증서·기기 시험을 요구하지 않는다. 번들의 해시 일치는 그 번들의 원본 소스 확보와 별개이며, 다른 후보의 성공을 현재 후보의 성공으로 합치지 않는다.

## 6 회고와 과도한 검토 중단 요청

```text
$specify-failure-recovery와 $review-release-evidence로 [수정 이력/회고 문서]를 검토해줘.
목표는 다음 프로젝트에 적용할 규칙과 명세 양식을 만드는 것이야.
초기 요구 누락과 구현·연결·시험 누락, 승인된 추가 범위를 원근거로 구분하고
문제→늦게 발견된 이유→최소 예방 규칙→사용 예로 정리해줘.
추가 시험·리뷰·스킬마다 어떤 미해결 결정을 바꾸는지 판단해줘.
전체 조사 상한은 [시간/범위]이고 방법을 바꿔도 유지해줘.
교차 검토의 수정분 확인 후 종료하고, 제품 수정·설치·장비 확보는 별도 목표로 남겨줘.
```

커밋·문서·시험 개수만으로 낭비율이나 절감 시간을 계산하지 않는다. 재사용 규칙이 기존 지침으로 충분하면 새 스킬을 만들지 않는다.

## 다른 PC와 프로젝트에 설치

먼저 아래 요청을 Codex에 그대로 전달한다. 두 폴더는 각각 단일 `SKILL.md`로 구성되며 추가 패키지나 실행 프로그램이 필요하지 않다.

```text
$skill-installer를 사용해 다음 GitHub 저장소의 두 스킬을 설치해줘.
저장소: https://github.com/jeonbyungryong/CODEX_NEW_SKILLS_261002
경로: skills/specify-failure-recovery
      skills/review-release-evidence
현재 환경이 지원하는 개인 스킬 위치를 사용해줘.
같은 이름이 이미 있으면 같은 내용은 건너뛰고, 다르면 차이를 보여준 뒤
기존 개인 수정본을 보존하는 업데이트 방법을 정해줘. 중복 이름으로 새로 설치하지 마.
설치 후 파일 일치와 사용 가능 목록을 확인해줘.
```

특정 프로젝트에만 넣고 팀원과 버전을 고정하려면 다음 요청을 사용한다.

```text
위 저장소의 두 스킬을 이 프로젝트의 .agents/skills/ 아래에 적용해줘.
먼저 개인·상위 폴더·프로젝트에서 같은 이름이 발견되는지 확인해줘.
이미 개인 설치로 사용할 수 있다면 중복 복사하지 말고 현재 설치를 사용해줘.
팀 공유를 위해 프로젝트 버전 고정이 필요하면 개인본과의 차이와 적용 범위를 먼저 제시해줘.
새 폴더 이름이나 별칭으로 같은 스킬을 복제하지 말고 원본 커밋과 변경 여부를 기록해줘.
```

수동 설치를 선택하면 각 폴더 전체를 지원되는 위치에 복사한다. 현재 공식 문서는 프로젝트의 `.agents/skills/`와 개인의 `~/.agents/skills/`를 안내하며, 설치 도구가 사용하는 기존 `~/.codex/skills/` 환경도 있다. 실제 도구의 설치 위치와 사용 가능 목록을 확인하고 같은 스킬을 두 위치에 중복 설치하지 않는다. 이 저장소의 `skills/` 폴더를 clone하는 것만으로 프로젝트에 자동 등록된다고 가정하지 않는다.

Codex는 스킬 변경을 자동 감지한다. 보이지 않으면 새 요청에서 확인하고 그래도 나타나지 않을 때 재시작한다. 명시적 호출은 `$specify-failure-recovery`, `$review-release-evidence`를 사용하며, 자동 선택은 스킬 설명과 현재 작업의 일치 여부에 따른다. [OpenAI 공식 스킬 문서](https://learn.chatgpt.com/docs/build-skills), 확인 2026-10-14.

## 중복을 피하는 선택 기준

| 이번 질문 | 사용할 지침 |
| --- | --- |
| 오류가 언제 발생하고 언제 다시 사용할 수 있는가 | `specify-failure-recovery` |
| 어떤 후보가 무엇을 검증했으며 이번 작업을 언제 끝내는가 | `review-release-evidence` |
| 이미 승인된 실기 시험을 사람과 agent가 어떻게 나눠 실행하는가 | 기존 `coordinate-device-validation` |
| 다른 Windows 셸에서 검증 스크립트가 같은 의미로 실행되는가 | 기존 `verify-powershell-handoff` |
| Windows native Computer Use가 어느 경계에서 실패했는가 | 기존 `diagnose-computer-use-recovery` |

두 스킬의 [배포 검증과 한계](planning-review-validation-20261014.md)를 함께 확인한다. 모든 단계에서 모든 스킬을 읽거나 호출할 필요는 없다.
