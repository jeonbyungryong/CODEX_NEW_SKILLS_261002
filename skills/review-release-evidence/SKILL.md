# 릴리즈 근거와 종료 판정

서로 다른 후보의 성공, 미검증, 사용자 위험 수용을 구분하는 인수인계 참고서다. 현재 요청이 검토이면 검토만 한다. 새 배포·원격 쓰기·기기 조작 권한을 만들지 않는다.

## 후보와 근거의 연결

실제 제품에 있는 구성요소만 다음 관계에 넣는다. 빌드가 없는 문서 검토에 APK나 인증서를 요구하지 않는다.

| 기록 | 확인할 관계 |
| --- | --- |
| 현재 결정 | 승인자·날짜·운영 범위·대체된 이전 기준 |
| 소스 | 저장소/ref/commit, 작업 변경 여부, 새 환경의 원본 접근 가능성 |
| 빌드 입력 | 별도 UI/서버/펌웨어 원본, lockfile, 버전, 도구 설정 |
| 산출물 | 해시·버전·필요시 서명, 실제 시험 또는 설치 대상과의 동일성 |
| 시험 | 후보·환경·전제·행동·관측·결과·원본 근거의 위치 |
| 후속 | 미검증·수용 제한·재개 조건·담당자·실행 권한 |

번들 해시가 맞아도 그 번들의 원본을 확보한 것은 아니다. Git 백업, 설치 파일, 서명키, 운영 데이터, 원본 미디어는 서로 다른 복원 대상이다. 비밀 값 대신 인계 담당·접근 방법·복원 확인 여부를 적는다.

## 판정 종류

`현재 결함`, `과거 해소`, `수용된 제한`, `미검증`, `개선 제안`을 구분한다. 실행 수준도 `소스 확인`, `모의 시험`, `호스트 통합`, `실제 대상 시험`으로 표시한다. 전체 숫자보다 해당 주장에 필요한 증거를 찾는다.

예: 후보 H4의 부팅 성공과 H5의 모의 timeout 시험을 합쳐 H5 실기 복구 PASS로 만들 수 없다. H5에서 일반 오류가 일정 시간 뒤 발생했다면 고유한 분기 관측이 없는 한 정확한 timeout 실증은 미검증이다. 사용자가 그 위험을 제한 운영으로 수용했다면 **범위 한정 완료**로 적고, 미검증 상태는 유지한다.

## 우선순위와 반복 중단

회고 요청의 완료 조건은 근거 있는 교훈과 재사용 규칙의 인계다. 제품 수정·설치·새 실행 환경 확보를 그 완료 조건으로 바꾸지 않는다. 제공 불가능한 장비는 실행 주장의 한계로 기록하며, 에뮬레이터도 현재 결정을 바꿀 관측에 필요할 때만 제안한다.

재개발 우선순위는 현재 운영 영향, 데이터·인증 안전, 빌드 재현을 막는 인계 공백, 그 뒤의 기능 개선 순으로 실제 사례에 맞춰 정한다. 각 제안에는 발생 상황·영향·최소 조치·미조치 결과를 붙인다. 초기 요구가 이미 있었는지와 이후 승인된 범위 확장인지도 구분한다.

다음 시험을 제안할 때 판정을 바꿀 질문, 새 관측, 같은 후보 여부, 횟수/시간 상한을 적는다. 같은 결과만 반복되면 원인·관측 방법이 달라질 때까지 중단하거나 현재 권한 안의 읽기 검토로 전환한다. 남은 미검증을 수용한 완료 결정을 과거 gate로 자동 재개하지 않는다.

추가 검증·리뷰·스킬마다 미해결 결정과 기존 근거로 답할 수 없는 이유를 명시한다. 전체 조사 범위와 상한은 방법을 바꿔도 유지한다. 교차 검토 후에는 발견 수정분을 확인하고 종료한다. 새 목표·권한·비용이 필요하면 현재 결과와 미검증을 인계하고 그 확대만 별도로 승인받는다.

## 흔한 오판

많은 커밋·문서·테스트를 비용이나 낭비율로 환산하는 것; 컴파일 실패를 실제 동작의 RED로 세는 것; snapshot이나 접수 응답을 실제 결과로 보는 것; 고정된 과거 배포 버전 검사를 현재 도구라고 인계하는 것. 줄바꿈 정규화로 해시가 달라졌다면 원본 바이트 해시와 정규화본 의미를 구분하고 증거를 조용히 덮어쓰지 않는다.
